### Cola de sincronización (outbox) — preparado para conectar la API real

- **El problema que resuelve**: la API todavía no existe, pero cuando exista no se puede perder ni un producto, movimiento, venta, proveedor o cliente cargado mientras tanto. La solución es un patrón **outbox**: cada escritura de negocio queda anotada en una cola local, en el orden en que ocurrió, lista para reproducirse contra la API en cuanto esté disponible.
- **`src/main/sync/outbox.ts`**: `encolarCambio(entidad, operacion, entidadId, payload)` agrega un registro a la colección `cambios_pendientes.json` (mismo mecanismo de `localStore.ts` que el resto de los datos) con `estado: 'PENDIENTE'`. `listarPendientes()` y `obtenerEstadoSync()` exponen lo que falta sincronizar (para uso futuro en la UI). `ejecutarSincronizacion()` recorre la cola **en orden de creación** e intenta reproducir cada cambio contra la API vía `enviarCambioApi()` — hoy esa función es un placeholder que siempre falla con un mensaje claro ("La API todavía no está configurada"), así que todo cambio queda marcado `ERROR` (no se descarta, no se pierde, y se reintenta la próxima vez que se ejecute la sincronización). El día que la API exista, **solo hay que reemplazar el cuerpo de `enviarCambioApi()`** por la llamada HTTP real; el resto del sistema (cola, orden, reintentos, estados) no cambia.
- **Quién encola qué**: `productos.ipc.ts` (crear/actualizar/eliminar), `stock.ts` (cada movimiento de inventario, más la actualización de stock del producto que ese movimiento genera — cubre tanto ajustes manuales como las salidas automáticas de una venta), `ventas.ipc.ts` (crear venta) y `proveedores.ipc.ts`/`clientes.ipc.ts` (crear/actualizar/eliminar, sin contar el sembrado del registro "general", que no es una acción del usuario). **Los usuarios (`usuarios.ipc.ts`) no se encolan a propósito**: la autenticación es local a este dispositivo y no hay todavía ninguna razón para asumir que la futura API comparte el mismo modelo de usuarios/roles — se puede sumar cuando se defina el contrato de la API.
- **Por qué preserva el orden en vez de comparar timestamps**: con un array simple que solo crece (`push`), reproducir la cola en el mismo orden en que ocurrieron los cambios evita, por ejemplo, sincronizar una venta antes que el producto que la sustenta. Un esquema de "último cambio gana" por timestamp no da esa garantía. Es la aproximación estándar para apps offline-first de un solo dispositivo (no hay que resolver conflictos entre dispositivos todavía).
- **IPC**: `sync:listar-pendientes`, `sync:estado`, `sync:ejecutar` (`registerSyncIpc` en `src/main/ipc/sync.ipc.ts`). Expuestos en `window.api.sync` y con su propio `sync.service.ts` en el renderer — **sin pantalla propia todavía**, a propósito: la UI de sincronización (por ejemplo, un badge con la cantidad de cambios pendientes o un botón "Sincronizar ahora") se deja para el trabajo de UI/UX al final, junto con el resto de la interfaz. El backend ya queda listo para que esa pantalla sea solo consumir el servicio.

### Respaldo de datos (backup automático + manual)

- **El problema que resuelve**: pediste explícitamente que los datos no se pierdan al actualizar la app. Los datos ya viven en `userData` (fuera de la carpeta de instalación, así que un update normal de Electron no los toca), pero igual puede haber un desinstalador que ofrezca "borrar datos de usuario", una reinstalación manual, o el día de mañana una migración de esquema que salga mal — el respaldo cubre esos casos.
- **`src/main/backup/backup.ts`**: `crearRespaldo()` copia todos los `.json` de `userData/data/` a una carpeta nueva `userData/backups/<timestamp-ISO>/`; devuelve `null` si todavía no hay datos que respaldar. Se llama **automáticamente al arrancar la app** (`main.ts`, antes de registrar cualquier IPC), así que siempre queda un snapshot del último estado conocido antes de que la sesión actual escriba nada — incluida la primera vez que se abre la app después de instalar una actualización. Guarda como máximo los **10 respaldos más recientes** (`limpiarRespaldosViejos`), para no llenar el disco con el tiempo.
- `listarRespaldos()` devuelve los nombres (timestamps) más recientes primero. `restaurarRespaldo(nombre)` copia los archivos de ese respaldo de vuelta a `data/`, **después de crear a su vez un respaldo del estado actual** (por si la restauración fue un error, no se pierde lo que había). Valida el nombre contra un patrón fijo de timestamp (vía `path.basename` + regex) antes de tocar el filesystem, para no confiar ciegamente en un string que llega por IPC.
- **IPC**: `backup:crear`, `backup:listar`, `backup:restaurar` (`registerBackupIpc`). Expuestos en `window.api.backup`, con `backup.service.ts` en el renderer. **Tampoco tiene pantalla propia todavía** — mismo criterio que la sincronización: es lógica ya lista, la pantalla ("Ver respaldos" / "Restaurar") se arma en la etapa de UI/UX.

### Imagen de producto

- **Cómo se guarda**: `Producto.imagenUrl` es un data URL en base64 (ej. `data:image/png;base64,...`), guardado como un campo más dentro del mismo `productos.json` — no hay archivos de imagen sueltos ni carpeta aparte. Se eligió esto en vez de guardar la imagen como archivo en disco (con un protocolo custom tipo `app://` para servirla al renderer) porque evita registrar un protocolo de Electron, evita limpiar archivos huérfanos al borrar un producto, y hace que la imagen viaje automáticamente con el resto del registro (incluida la cola de sincronización: cuando se suba a la API real, la imagen ya va incluida en el `payload`, sin lógica extra). El costo es que `productos.json` pesa más — aceptable para el volumen esperado de esta app.
- **Cómo se sube**: en `ProductoForm`, un `<input type="file">` limitado a `image/png|jpeg|webp|gif`; el archivo se lee en el propio renderer con `FileReader.readAsDataURL` (no hace falta IPC para leer el archivo del disco del usuario) y el resultado se manda como parte del mismo payload de `crear`/`actualizar` que ya existía. Hay un botón "Quitar imagen". `ProductoDetalle` la muestra si existe.
- **Validación** (cliente y `productos.ipc.ts`, mismo patrón que el resto de las reglas de negocio): formato debe ser PNG/JPG/WEBP/GIF, tamaño máximo ~2MB. En el cliente se valida contra `File.size` (bytes reales) antes de leer el archivo, para fallar rápido; en el proceso `main` se valida contra el largo del string base64 recibido (que pesa ~4/3 del archivo original), como red de seguridad porque ahí es donde de verdad se puede confiar en la validación.

> **Nota sobre un bug real que hubo acá:** al probar, la imagen se guardaba bien (sin errores) pero no se veía en pantalla. No era un límite de dimensiones ni de tamaño — la Content-Security-Policy de `src/renderer/index.html` tenía `default-src 'self'` sin declarar `img-src`, así que el navegador bloqueaba silenciosamente cualquier `<img src="data:...">` (el error solo aparecía en la consola de DevTools). Se corrigió agregando `img-src 'self' data:` a la política, sin aflojar el resto (`script-src`/`style-src` siguen igual de estrictos). Detectado y corregido el 2026-07-17.

### Gestión de usuarios

- CRUD completo vía IPC (`usuarios:listar/obtener/crear/actualizar/eliminar`), en `Configuración → Gestión de usuarios` (solo visible/accesible para `ADMIN`, protegido con un guard de rol `RequireRole` en el router, además de que el link solo se muestra a admins en la UI).
- Reglas de negocio en `src/main/auth/usuarios.repository.ts`: no permite emails duplicados (case-insensitive) y **no deja eliminar al último usuario ADMIN** (evita quedarse sin forma de entrar a la app).
- En la UI: no se puede eliminar el propio usuario logueado (botón deshabilitado); al editarse un cambio de contraseña es opcional (dejar vacío no la toca); si un admin edita su propio usuario, la sesión en memoria (Zustand) se refresca al toque para no mostrar datos viejos en el Header.
- **Límite conocido**: la autorización por rol hoy es solo de UI (el proceso `main` no valida quién llama por IPC). Es un riesgo aceptable porque el renderer es código propio, no contenido web arbitrario — pero si algún día se expone contenido no confiable en el renderer, hay que agregar verificación de sesión en el propio handler IPC, no solo en las rutas.

### Datos locales (productos, inventario y ventas)

- Los productos, movimientos de inventario y ventas se guardan en JSON dentro de la carpeta de datos de usuario de Electron (`app.getPath('userData')/data/*.json`), no en el proyecto.
- CRUD completo de productos vía IPC (`productos:listar/obtener/crear/actualizar/eliminar`), **con las pantallas ya conectadas**: `ProductoForm` crea y edita de verdad (SKU, nombre, descripción, precio, stock inicial, stock mínimo) y `ProductoDetalle` muestra los datos reales con link a editar.
- Movimientos de inventario (`ENTRADA`/`SALIDA`/`AJUSTE`) vía IPC, y **actualizan el stock del producto correspondiente** al registrarse. La lógica vive en `src/main/inventario/stock.ts`, compartida entre el módulo de inventario y el de ventas. `AjusteInventario` tiene un selector real de productos (con stock visible) y registra el movimiento de verdad.
- **El stock de un producto solo se cambia por dos caminos:** el stock inicial al crearlo, o "Ajuste de inventario" (que deja rastro en `movimientos`). Al editar un producto existente el campo stock es de solo lectura a propósito, para que el historial de movimientos siga siendo la fuente de verdad y no se pueda pisar el stock sin dejar rastro.
- **Ventas conectadas de punta a punta**: `NuevaVenta` tiene un selector real de productos (con stock visible) que arma el carrito; al confirmar, se valida stock disponible, se calcula el total en el proceso `main` (no se confía en el total calculado en el renderer), se guarda la venta y se generan movimientos `SALIDA` automáticos que descuentan el stock. `HistorialVentas` lista las ventas guardadas.
- Los servicios del renderer (`productos.service.ts`, `inventario.service.ts`, `ventas.service.ts`) ya no llaman a `axios`/API remota — hablan directo con el proceso `main` vía `window.api` (preload con `contextBridge`). Se eliminó la dependencia `axios` y `api.client.ts` del proyecto (cero usos); se vuelve a agregar cuando arranque el trabajo de conectar la API real (pendiente #7).

> **Nota sobre un bug real que hubo acá:** cuando se armó el backend local de productos/inventario, se dejaron sin conectar las pantallas `ProductoForm` y `AjusteInventario` — el backend funcionaba (por eso `NuevaVenta` y `ProductosList` ya andaban), pero los formularios de "Nuevo producto" y "Ajuste de inventario" seguían siendo el stub original del scaffold (`// TODO: llamar al service`) y no guardaban nada al enviarlos. Se detectó al revisar el estado del proyecto y se corrigió el 2026-07-17.

### Proveedores y Clientes

- CRUD completo vía IPC para ambos (`proveedores:listar/obtener/crear/actualizar/eliminar`, `clientes:...` igual), guardado en `userData/data/proveedores.json` y `clientes.json`.
- Pantallas `ProveedoresList`/`ProveedorForm` y `ClientesList`/`ClienteForm` (crear + editar), mismo patrón que Usuarios: lista con tabla, link "Editar", botón "Eliminar" con manejo de error.
- Son entidades simples (sin reglas de negocio como unicidad o timestamps), así que no tienen "Detalle" separado — el propio formulario de edición cumple ese rol, igual que con Usuarios.
- **"Proveedor general" y "Cliente general"**: se siembran automáticamente en el primer arranque (`esGeneral: true` en el tipo `Proveedor`/`Cliente`), sin info adicional (solo nombre). Igual que con el admin por defecto, la app garantiza que siempre exista al menos un proveedor y un cliente seleccionables, para no obligar a crear uno real antes de poder cargar un producto o cerrar una venta.
- **Protegidos contra borrado**: `PROVEEDORES_ELIMINAR`/`CLIENTES_ELIMINAR` rechazan la operación si el registro tiene `esGeneral: true` (mismo patrón que "no se puede eliminar al último admin"). En la UI el botón "Eliminar" aparece deshabilitado para esos registros, con tooltip explicando por qué. Sí se pueden editar (por si se quiere, por ejemplo, renombrarlos).
- **Asociación con Productos y Ventas**: `ProductoForm` tiene un selector de proveedor (precargado con "Proveedor general" al crear uno nuevo) y `ProductoDetalle` muestra el nombre del proveedor. `NuevaVenta` tiene un selector de cliente (precargado con "Cliente general") y `HistorialVentas` muestra el cliente de cada venta.

### Validación de formularios y reglas de negocio

- **La fuente de verdad es siempre el proceso `main`**, no el formulario: cada regla se aplica en el handler IPC (donde se puede confiar) y además en el formulario (para dar feedback inmediato sin esperar el viaje por IPC). Si algún día se agrega otro cliente (por ejemplo una API HTTP), las reglas de negocio siguen protegidas aunque ese cliente no valide nada.
- **Productos** (`productos.ipc.ts`): SKU obligatorio y único (case-insensitive, tanto al crear como al editar), nombre obligatorio, precio/stock/stock mínimo no pueden ser negativos. `ProductoForm` repite estas mismas validaciones antes de llamar al servicio, mostrando el mensaje en el mismo lugar que los errores del backend.
- **Movimientos de inventario** (`src/main/inventario/stock.ts`): cantidad debe ser mayor a 0 para `ENTRADA`/`SALIDA`; para `AJUSTE` (que fija el stock exacto) se permite `0` pero no negativos; una `SALIDA` no puede dejar el stock en negativo. Esta validación quedó centralizada en `registrarMovimiento`, así que protege tanto los ajustes manuales como los descuentos de stock que genera una venta. `AjusteInventario` valida lo mismo del lado del cliente y ya no fuerza `min={1}` en el campo cantidad cuando el tipo es `AJUSTE` (antes ese límite no dejaba fijar el stock en 0 aunque fuera algo válido — era un bug real, no solo falta de validación).
- **Login**: recorta espacios del correo antes de enviarlo y muestra "Completá el correo y la contraseña" si falta alguno, en vez de depender solo del `required` nativo del navegador.

### UI/UX — pase de diseño, pantalla por pantalla

- **Stack elegido**: `antd` (Ant Design v6) como librería de componentes + Tailwind CSS v4 (`@tailwindcss/vite`) para maquetar layout/espaciado. ## 🟡 Decisiones tomadas a propósito (no son huecos)

- **Storage: JSON plano, no SQLite/electron-store.** Se evaluó `electron-store` pero su versión actual es ESM-only y choca con cómo `electron-vite` empaqueta el proceso `main` (CommonJS + `externalizeDeps`). Se optó por `node:fs` + `node:path` directo: cero dependencias, cero riesgo de romper con futuras actualizaciones. Fácil de migrar a SQLite/API real después porque toda la lectura/escritura pasa por `src/main/store/localStore.ts`.
- **Hashing con `node:crypto` (scrypt), no `bcrypt`/`bcryptjs`.** Mismo motivo: la versión actual de `bcryptjs` también es ESM-only. `scrypt` es nativo de Node, seguro, sin dependencias.
- **Sesión no persiste entre reinicios de la app.** Cada vez que se abre la app hay que loguearse de nuevo. Es razonable para una app tipo POS/inventario donde importa saber quién es el usuario activo en cada sesión de trabajo. Se puede cambiar a persistente (`zustand/persist`) si se prefiere.
- **El total de una venta se recalcula en el proceso `main`**, no se confía en el total que mande el renderer — evita que un carrito manipulado en el cliente falsee el total cobrado.

## Notas técnicas (para no repetir errores ya resueltos)

- **El proyecto usa TypeScript 5.9.x, no 7.x.** Se arrancó en TS7 (ver notas de abajo) pero se bajó a 5.9 cuando `typescript-eslint` resultó incompatible con TS7. Si en el futuro se vuelve a subir a TS7, hay que reverificar que todo el toolchain de lint ya lo soporte.
- **TypeScript 7 eliminó `baseUrl`** (dato histórico, sigue aplicando aunque ya no estemos en TS7 porque la sintaxis sin `baseUrl` también es válida en TS5) — los `paths` en `tsconfig.json`/`tsconfig.main.json` deben ser relativos con `./`.
- **electron-vite prohíbe el archivo `vite.config.ts`** — el config se llama `electron.vite.config.ts`.
- El alias `@shared` debe declararse en las tres secciones (`main`, `preload`, `renderer`) de `electron.vite.config.ts`, no solo en `renderer`.
- **React 19 eliminó el namespace global `JSX`** — hay que importarlo explícitamente: `import type { JSX } from 'react'`.
- **Zustand v5 requiere el patrón curried** `create<T>()((set) => ...)` para que la inferencia de tipos funcione.
- Versiones de `vite`/`electron-vite`/`@vitejs/plugin-react` están fijadas deliberadamente (vite `^7`, no `^8`) porque `electron-vite@5` todavía no soporta Vite 8.
- **Este sandbox de desarrollo tiene `ELECTRON_RUN_AS_NODE=1`**, lo que impide levantar la ventana de Electron desde aquí (el binario corre como Node plano). No es un problema del proyecto — `npm run dev` sí abre la ventana en un entorno normal con pantalla.
- **Patrón outbox para la futura sincronización**: se evaluaron tres enfoques (timestamps + last-write-wins, cola de cambios en orden, bandera de sincronizado por registro) y se optó por combinar cola + estado por registro (ver sección "Cola de sincronización" en "Hecho"). La razón de fondo: con un solo dispositivo y sin API todavía, lo que importa es no perder ninguna operación y poder reproducirlas en el orden correcto — comparar timestamps recién sería necesario si en algún momento hay más de un dispositivo escribiendo al mismo tiempo.
